## 工具限制及后续实机验收

自动化工具向单个应用发送的模拟按键没有触发 Carbon 全局热键；工具也无法通过普通窗口绑定访问无主窗口的 KeyPilot 菜单栏进程。用户实际按键已证明热键可进入并显示标签。工具明确禁止操作当前 ChatGPT/Electron 应用，因此未改用另一个接口绕过。

以下仍需真实键盘和用户反馈：

- 原生、Electron、Safari 中的连续 J/K、Shift 加速、两键同时按、加载期间按住接续，以及真实端点反馈。
- 点击后导航保持、右键/Command 点击、临时中文输入、应用快捷键透传和跨模式配对。
- Safari 等应用中各种非标准浮层的完整标签覆盖；AX 没有暴露标准角色/关系的自绘元素无法保证。
- 实际多显示器、桌面切换、锁屏/睡眠、系统强制 tap 超时和较慢 AX 应用下的恢复表现。
- macOS 13/14 与 Intel 机器上的运行验证。本次只在 macOS 15.8 Apple Silicon 安装检查。

窗口暂时不可读会保留边框并退避，但旧坐标不执行；超过扫描预算的集合标记不完整。上述边界不会用按应用名称写特例、OCR、录屏或后台永久轮询来掩盖。

## 本轮发现并修复的问题

启动时主动停用 tap 的系统通知曾造成重复退出循环，已增加幂等停用和空闲/迟到通知门控。代码复核还修复了前缀未完成时 Return 复用旧选择、跨扫描复用旧区域、浮层点击校验继承原区裁剪、编码分配阻塞输入队列，以及端点透明度叠加问题。

build 4 的诊断捕获了具体链路：松键安排 450 ms 刷新，下一轮扫描进入后因 `ax_foreground_mismatch` 退出导航。这解释了后续标签消失；诊断没有记录实际进程身份，因此不能断言是哪个应用或哪种浮层导致 AX 焦点不一致。build 5 使用 `NSWorkspace.frontmostApplication`（系统定义为接收键盘事件的应用）进行扫描和动作前校验，不再以 AX 全局焦点的瞬时差异退出。实际切应用仍退出；未知前台拒绝动作。覆盖窗口改为 `.nonactivatingPanel`，明确不可成为 key/main 窗口，相同前台的重复激活通知不再中断导航。

build 5 同时加入原生毛玻璃标签、浅蓝白底色、薄荷绿选中态、圆角、细亮边与轻阴影，并遵循系统减少透明度设置。诊断时间戳在事件发生时采集，避免异步写文件延迟污染时间顺序。具体恢复效果待用户对 build 5 再确认。

## build 11：滚动列表分组时保留侧栏大区

用户报告会话大区滚动后间歇缺少索引。最近一次导航日志显示松键后 450 ms 刷新正常执行，扫描均完整完成；一轮滚动后大区数量由 3 降为 2，发现 129 个候选，其中 60 个被选区范围过滤，当前页仍有 69 个标签。未出现扫描失败或导航退出。证据见 `artifacts/scroll-labels-build10-before.json`。旧日志未记录原选区是否保留，也不记录应用/会话内容，不能仅靠这些计数认定实际丢失的是哪组控件。

代码中存在可复现的错误路径：将裸 AXList 内容分组优先当作侧栏视口；该分组滚出可见区域后不再满足大区阈值，原选区消失并回退到主内容区，仍可见的其他会话行因此被范围过滤。新增注入图将两组列表沿侧栏滚动，在修改前复现选区跳走及会话行无索引。现在优先保留已识别的同列外层侧栏，内容分组不再独立成为大区；真实滚动列表和原生 Outline/Table 继续保留独立视口身份，单独出现的列表仍可作为后备大区。

另一个回归覆盖推断侧栏的裁剪：滚出侧栏但仍在窗口内的行不会生成索引，边缘行裁至可见部分，属于该侧栏的浮动菜单继续按自身边界显示。点击前也复验对应区域祖先，所需边界不可读时不点击。两项新用例修改前共八处断言失败，修改后连同原生 Outline 保护用例共 54 项通过，见 `artifacts/scroll-labels-build11-before.txt`、`artifacts/scroll-labels-build11-after.txt`。

## 隐藏候选排查：尚未发布新构建

已保存本次前后的计数日志到 `artifacts/visibility-build12-before.json`。日志不包含按钮正文、像素或 CSS 状态，无法据此区分悬停隐藏与滚动裁剪。当前代码过滤 AXHidden、禁用状态、空矩形与已知祖先裁剪，点击前另做命中校验，但发布标签前没有等价的视觉可见性保证。

Apple 的 [AXVisibleChildren 文档](https://developer.apple.com/documentation/applicationservices/kaxvisiblechildrenattribute) 定义了可见直接子项，但它是推荐属性，不能假设每个应用都提供可靠集合。核查 Chromium 主分支 [browser_accessibility_cocoa.mm](https://raw.githubusercontent.com/chromium/chromium/main/ui/accessibility/platform/browser_accessibility_cocoa.mm) 的 `visibleChildren` 实现直接返回 `accessibilityChildren`；其 [Offscreen, Invisible and Size 文档](https://chromium.googlesource.com/chromium/src.git/+/HEAD/docs/accessibility/browser/offscreen.md) 也明确透明度为零不按 invisible 处理。因此不能把“增加可见子项读取”当作该反馈的已验证修复，也不能以缺少 AXHidden 属性就证明肉眼可见。

用户已明确回复“鼠标移上去才显示的按钮，例如更多、复制或编辑”，排除了本次主要是在报告滚出边缘的按钮。此反馈确认问题类别，但没有直接证明当前应用使用了哪种 CSS 隐藏方式。

继续核对平台接口：[AXHidden](https://developer.apple.com/documentation/applicationservices/kaxhiddenattribute) 的标准语义是应用是否隐藏，不是控件 CSS 透明度。Apple 提供 [AlternateUIVisible](https://developer.apple.com/documentation/appkit/nsaccessibilitycontainstransientui/isaccessibilityalternateuivisible%28%29) 表达悬停替代界面，但它要求目标实现对应协议，不能把未知/不支持当作隐藏。所核查 Chromium 主分支的 `browser_accessibility_cocoa.mm` 没有该属性、ShowAlternateUI 或透明度实现，且可见子项直接返回全部子项；源码检查摘要见 `artifacts/hover-visibility-source-check.json`。这不是对当前已安装 Codex 实现的直接检查。

在目标不提供视觉状态的情况下，透明而仍可命中的按钮与可见按钮可能拥有相同的 AX 角色、矩形及动作信息。点击命中检查只能校验动作对象，不能证明像素可见。因此目前“只读 AX、不录屏、不按应用或按钮名称写特例”的方案无法保证过滤这类悬停标签。未添加按按钮名、大小或鼠标距离猜测的规则，避免误删正常控件；未重新构建或安装，仍保留已确认滚动正常的 build 12。这项兼容性限制需要目标应用提供可靠状态或引入原约束以外的信息才能进一步解决。
